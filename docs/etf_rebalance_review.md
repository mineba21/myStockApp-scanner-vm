기존 개별 종목 매도 API의 부분수량 미리보기는 참고용으로 남겼지만 실행은 막았다.
새 사이클의 매도 미리보기는 설정 범위에서 **목표 초과수량만** 주문한다.
목표 수량과 같으면 거래하지 않으며, 목표 비중이 0이 된 종목은 전량 매도한다.
새 사이클에 `mode=DELTA_V1`을 저장한다. 이전 전량매도 payload는 자동 변환·실행하지 않고 대조/재검토 사유로 차단한다.

흐름:

1. 월간 보고서 + 전용 소유 범위 + 완전한 잔고/미체결 스냅샷 → SELL_PREVIEW.
2. 사용자 확인 → 주문 의도 영속 저장 → SELL_PENDING. 접수로 현금을 늘리지 않는다.
3. 계획한 조정 매도의 전량 체결 **및** 대상 보유수량이 유지 예정 수량과 일치 **및** 미체결 없음 → SELL_CONFIRMED.
4. 순주문가능 현금 + 유지 중인 보유수량 + 최신 지정가 재조회 → 부족수량만 BUY_PREVIEW. 사용자가 새 수량/예산을 다시 확인.
5. 확인 → BUY_PENDING → 매수 전량 체결 및 미체결 없음 → COMPLETE.

부분체결/미체결/취소/거절은 상태·종목·잔여수량을 blocker로 반환한다.
불명 주문은 고유한 주문내역 대조가 없으면 진행할 수 없다. 완료된 같은 사이클 키로
새 미리보기를 요청해도 기존 기록만 반환한다. 다른 키도 진행 중인 account2를 우회하지 못한다.
만료된 미전송 매도 미리보기는 같은 사이클에서 갱신하고 다시 확인한다.
매수 미리보기 역시 재계산만 허용하며 전송된 사이클은 새 preview로 초기화할 수 없다.

## 예산, 범위, 실연결의 제한

`ALLOCATION_LIQUIDATION_SCOPE`는 기존 설정명을 호환 유지하며, 의미는 **자산배분 전용 소유가 확인된 관리 ETF 티커** 목록이다. 목록에 있다는 이유만으로 전량 매도하지 않는다.
현재 목표에 없는 이전 달 ETF도 여기에 명시해야 전량 매도 대상이 된다. 기본값은 비어 있으며 자동으로
account2 전체를 넣지 않는다. 같은 ETF 티커에 다른 전략 수량이 섞였다면 이 설정으로 소유권을
분리할 수 없으므로 먼저 전략별 수량 원장이 필요하다. 이번 구현은 그 원장을 임의로 추정하지 않는다.

`ALLOCATION_JOURNAL_PATH`는 모든 worker가 공유하는 **단일 호스트의 영속 로컬 디스크** 파일이다.
미설정 시 차단한다. 다중 호스트/별도 DB 파일 간 중복 방지는 지원하지 않는다.
이 파일을 삭제·임시 디스크로 설정·오래된 백업으로 덮어쓰면 중복 방지 근거를 잃는다.
운영 서비스 전환 전에 기존 주문내역을 대조하여 이전 메모리 방식의 미확정 주문도 정리해야 한다.

목표 정수주는 `floor((순주문가능 현금 + 관리 보유수량 × 최신 가격의 합) × 월별 목표 비중 / 해당 가격)`이다.
목표가 보유수량보다 작으면 초과분만 매도하고, 크면 부족분만 매수한다.
계획용 자산과 주문 재원은 분리한다. 실제 매수 예산은 `순주문가능 현금 × (1 - ALLOCATION_RESERVE_BPS / 10000)`.
여유금 때문에 보유 중인 정상 목표수량을 줄여 팔지 않도록 목표비중 계산에는 여유금을 적용하지 않는다.
부족분의 합계가 매수 예산을 넘으면 부족분 비율대로 수량을 줄이고 종목별 정수주로 내림한다.
남은 금액은 현금으로 남긴다. 매수 단계에서 시세·현금 변동으로 추가 초과 보유가 계산되더라도
새 매도는 자동 실행하지 않고 `remaining_sell_adjustments`와 화면 경고로 표시한다.
매도·매수할 수량이 없는 단계는 사용자 확인과 잔고 검증만 진행하며 주문을 전송하지 않는다.
기본값 100bps(1%)는 수수료·반올림 등에 대한 보수적 운영 여유금이며 **실제 증권사 수수료율이 아니다**.
지정가가 원금 상한을 제한하며 가격을 변경하면 새 미리보기와 확인이 필요하다.
배분비율은 재정규화하지 않아 전략이 남긴 현금 비중을 보존한다. Decimal로 각 종목 정수주를
계산하고 총 주문금액을 예산과 비교한다. 이미 증권사 현금에서 차감된 미체결 예약금을 다시 빼지 않는다.
각 후속 매수 전에도 현금을 조회하며 부족하면 아직 전송하지 않은 의도를 PREPARED로 남긴다.
가격/잔고 시각은 최대 60초, 미래/NaN/누락 시각은 차단. 시세 원시각에서 유효기간을 계산한다.

[키움 공식 API 안내](https://openapi.kiwoom.com/m/guide/apiguide?jobTpCode=07)에서
`ust21050`(미국주식 원장 미체결), `ust21150`(일별 주문체결내역), `ust21180`(기간별 주문내역)의
존재는 확인했다. 하지만 이 저장소에 해당 대조 구현은 없고 `fc_ord_alowa`의 미체결 예약금·수수료
반영 의미도 검증되어 있지 않다. 이름만 보고 순현금이라고 가정하지 않았다.

따라서 실제 서비스 팩토리는 **UnavailableBroker**를 연결한다. 환경변수만 켜서 주문을
통과시키는 우회 경로는 없다. 매도 첫 단계부터 차단한다. 정상 전체 흐름은 모의 어댑터로 구현·검증했다.
실제 시세 응답의 원시각 파서도 미구현이므로 live sizing은 계획용 참고값이며 유효 주문 계획으로 표시하지 않는다.

실연결에 앞서 별도 구현/검증할 사항:

- account2/USD, 잔고·주문내역 전체 페이지/조회 범위/기준시각을 검증한 스냅샷.
- `snapshot()`의 `cash_includes_reservations=True`를 뒷받침하는 증권사 계약 및 모의 API 검증.
- `lookup(intent)`에서 계좌/거래일/주문번호/방향/종목/수량/가격의 고유 대조.
  응답 유실 시 후보 0개/여러 개는 미확정. 빈 주문내역만으로 미접수를 확정하지 않는다.
  모의 어댑터의 `matched_intent_id`는 이 검증을 완료했다는 내부 계약이며 HTTP 입력이 아니다.
- 취소/거절/중단된 PREPARED 의도를 사람이 증거와 대조하여 복구하는 절차.
  현재 자동 취소·자동 재전송·사이클 강제 종료는 제공하지 않는다.
- 실제 계좌 변경/저널 이전, API 인증을 포함한 배포 UI 검증. 이번 작업에서 실계좌 검증하지 않음.

## 격리 테스트

`tests/conftest.py`가 임시 SQLite URL, 비어 있는 알림 설정, 임시 자격증명 경로,
실행 비활성화와 전용 임시 저널을 주입한다. 새 테스트는 모의 broker/session만 사용한다.
운영 서비스 시작, 실제 가격 조회, 주문, Slack/Telegram 전송은 실행하지 않았다.

커버한 시나리오:

- 조정 매도 접수만으로 매수 불가 → 체결/유지수량/미체결 확인 → 현금 재조회 → 다시 확인 후 부족분 매수.
- 동일 종목·동일 수량은 주문 0건, 비중 변경은 초과/부족분만 거래, 종목 교체 시 공통 종목 유지.
- 추가 입금 및 현금 비중 유지, 유지수량 변동 시 매수 차단, 이전 전량매도 계획 실행 차단.
- 부분체결/미체결/취소/거절과 잔여 보유분, 체결내역의 잘못된 매칭.
- 빈 JSON/코드 누락/주문번호 누락·0·잘못된 형식, 전송 타임아웃.
- 동시 클릭, 반복 확인, 다른 profile 미리보기, 별도 프로세스에서 저널 복구,
  전송 후 프로세스 종료(SENDING 유지), 같은 완료 사이클 재사용.
- 여러 ETF의 합산 예산, 예약금 이중 차감 방지, 확인 직전/주문 사이의 현금 감소.
- 범위 밖 다른 전략의 보유종목 유지, 소유범위 미설정 시 차단.
- 잘못된 배분·누락/오래된 시세, 캐시 갱신 실패, 기존 execute 우회 차단.
- FastAPI HTTP 미리보기 → 확인 → 대조 → 매수 미리보기 → 확인 경로.

차액 방식 변경 후 최종 검증: `.venv/bin/python -m pytest tests/ -q` → **503 passed, 7 warnings, 18.55초**.
추가한 차액 시나리오 6개를 포함하며 기존 주문 안전성 테스트도 모두 통과했다.
경고는 기존 FastAPI/Starlette/SQLAlchemy 사용 중단 예고다. 변경 Python 파일의
`py_compile`, 템플릿 내 모든 인라인 스크립트의 `node --check`, `git diff --check`도 통과했다.
로그인된 실제 브라우저/증권사와의 화면 연동 검증은 이번 테스트 범위에 포함하지 않는다.

## 개별주 후속 작업 (코드 변경 없음)

1. **D+3 확정 유지 — 의도된 사후 평가.** `scanner/entry_control.py:evaluate_upthrust`는
   D+1..D+N이 모두 채워질 때까지 `(None, None)`을 반환한다고 명시한다.
   `tests/test_entry_controls.py:test_upthrust_pending_then_true_or_false`도 이를 검증한다.
   해당 Step 4 전용 MD는 없다. 이를 명백한 구현 오류로 단정하지 않는다.
   **후속 제안:** D+1~D+2 피벗 이탈을 별도 early-warning 필드로 추가하되 기존 확정 필드를 바꾸지 않는다.
   입력 일봉의 장 마감 여부·NaN 여부 검증도 별도 확인한다.
2. **경고 전용 기본값 유지 — 의도된 동작.** `config.py`의 Step 4 shadow-first 주석 및
   `PIVOT_EXT_AS_GATE`, `UPTHRUST_AS_GATE`, `ALERT_FRESHNESS_AS_GATE=false`가 근거다.
   `scanner/strict_filter.py:_check_entry_controls`는 토글을 켰을 때만 차단한다.
   `scanner/scan_engine.py`는 entry_warnings를 저장하고 알림 본문에도 출력하지만,
   `web/app.py:/api/results`에는 entry_warnings/upthrust_failed가 노출되지 않아 카드 표현 연결이 부족하다.
   **후속 제안:** API·카드에 경고/보류/확정 상태를 전달하고 경고 기본값을 유지하는 회귀 테스트 추가.
   차트의 현재가 피벗 하향 경고(`_build_scan_overlay`)는 이미 별도로 있으므로 재사용 여부 검토.
3. **진행 중 주봉 조기 경고와 확정 판정 구분 — 표시 개선 제안.** Step 1 항목 3/5/8은
   거래량 basis와 다른 지표의 불변 계약을 명시한다. 현재 `compute_weekly_indicators`/
   funnel은 CURRENT_NORMALIZED/PREVIOUS_COMPLETE/CURRENT_COMPLETE를 구분하지만
   결과 카드·알림에 그 기준과 확정 여부가 일관되게 전달되지 않는다.
   **후속 제안:** 진행 주봉 기반 경고와 완료 주봉 판정의 기준시각·배지를 분리.
   거래일 캘린더/금요일 장중/피드 지연 검증을 먼저 하고 전략 판정식을 임의로 바꾸지 않는다.
